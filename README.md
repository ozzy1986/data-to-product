# Карточка товара КИП из данных о приборе

Прототип сервиса: по JSON с данными о контрольно-измерительном приборе LLM пишет черновик
карточки товара для B2B-интернет-магазина:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1200 символов;
- таблица ключевых характеристик;
- 3–5 поисковых запросов;
- блок для менеджера: кому подходит прибор и какие задачи решает;
- список того, что нужно уточнить, и предупреждения о том, что не прошло автоматическую проверку.

**Демо:** https://data-to-product.ozzy1986.com. Это веб-форма и HTTP API. Готовые примеры
открываются кнопками «Примеры» даже тогда, когда модель офлайн (подробнее в разделе «Демо на VPS»).

Стек: Python 3.12+, FastAPI, LLM через [Ollama](https://ollama.com) (по умолчанию `gemma3:4b`,
бюджет 0 $). Базы данных нет.

## Главное: модель не выдумывает характеристики

Одного промпта для этого мало, особенно с моделью на 4B параметров. Поэтому задача разделена между
моделью и кодом:

| Что | Кто делает | Почему так |
|---|---|---|
| Таблица характеристик | **код**, только из `specs` входа | значение в таблице физически не может прийти от модели |
| Характеристики, которых не хватает | модель называет **только названия**, код ставит значение «данных нет» | модель знает, что важно для манометра, но значений не пишет |
| Пробелы во входе (нет производителя, пустое значение, обрезанное описание) | **код**, ещё до вызова модели | детерминированно, не зависит от модели |
| Тексты: заголовок, описание, запросы, блок для менеджера | модель | для этого LLM и нужна |
| Сверка чисел в текстах со входом | **код** | каждое число в ответе должно встречаться во входных данных (`1,6` = `1.6`, `02` = `2`) |
| Длина заголовка и описания, число запросов | **код** | маленькая модель плохо считает символы |

Если ответ не прошёл проверки, модель получает конкретные замечания и пишет ответ заново, максимум
`LLM_REPAIRS=2` раза. Замечания указывают поле и фрагмент: «search_queries: число «16» отсутствует во
входных данных (манометр 0 16 мпа)». Из всех попыток сервис берёт ответ с наименьшим числом проблем.
Что исправить не удалось, уходит в `warnings`: менеджер видит, какое место перепроверить.
Заголовок длиннее 70 символов код обрезает по границе слова и тоже пишет об этом в `warnings`.

## Быстрый старт

Нужны Python 3.12+ и Ollama.

```bash
ollama pull gemma3:4b
```

```bash
python -m venv .venv
```

```bash
.venv/Scripts/pip install -r requirements-dev.txt
```

(на Linux и macOS вместо `.venv/Scripts/` пишется `.venv/bin/`)

```bash
.venv/Scripts/python -m uvicorn app.main:app --port 8103
```

Затем откройте http://127.0.0.1:8103: там форма (поля или сырой JSON) и кнопки с примерами.

### Из консоли, без веб-сервера

```bash
.venv/Scripts/python -m app.cli examples/input/dm02.json
```

Команда печатает Markdown. С флагом `--json` выводится JSON, с `--out examples/output` для каждого
входного файла сохраняются `<имя>.json` и `<имя>.md`. Именно так получены примеры в репозитории.

### Тесты

```bash
.venv/Scripts/python -m pytest -q
```

43 теста работают без Ollama: вместо модели подставляется `FakeLLM` с заранее заданными ответами.
Проверяются разбор и валидация входа, поиск пробелов, сверка чисел, повтор с замечаниями, выбор
лучшей попытки, обрезка заголовка, кэш и коды ответов API.

### Настройки (переменные окружения)

| Переменная | По умолчанию | Что это |
|---|---|---|
| `LLM_URL` | `http://127.0.0.1:11434` | адрес Ollama |
| `LLM_MODEL` | `gemma3:4b` | модель |
| `LLM_TIMEOUT` | `240` | секунд на один вызов модели |
| `LLM_NUM_CTX` | `4096` | контекст; промпту с повтором хватает, и модель целиком помещается в 4 ГБ видеопамяти |
| `LLM_REPAIRS` | `2` | сколько раз повторять запрос с замечаниями |
| `LLM_TEMPERATURE` | `0.3` | температура |
| `QUEUE_LIMIT` | `4` | сколько запросов ждут модель; при переполнении сразу 503, без долгого таймаута |
| `CACHE_SIZE` | `256` | готовых карточек в памяти (ключ — хэш входа, модели и версии промпта) |
| `MAX_BODY_BYTES` | `64000` | предельный размер запроса |

Ключей API нет: модель локальная. Если подключить внешнюю модель, её ключ должен лежать в
переменной окружения (на сервере это `shared/.env`, права 600), а не в коде. Файлы `.env` в git не попадают.

## API

`POST /api/generate` с телом в виде JSON о товаре:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {"диапазон измерений": "0–1,6 МПа", "класс точности": "1,5", "присоединение": "G1/2", "диаметр корпуса": "100 мм"},
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Обязательно только поле `name`. Без остальных полей карточка тоже собирается, а пробелы
перечисляются в `missing`. Значения `specs` могут быть строками, числами, `true`/`false` или
списками строк.

Ответ `200`:

```jsonc
{
  "card": {
    "seo_title": "…",
    "seo_description": "…",
    "specs": [{"name": "Диапазон измерений", "value": "0–1,6 МПа", "source": "input"},
              {"name": "Степень защиты корпуса", "value": "данных нет", "source": "missing"}],
    "search_queries": ["…"],
    "commercial": {"audience": ["…"], "tasks": ["…"]}
  },
  "missing": ["Описание обрывается многоточием…", "Нет данных: степень защиты корпуса — уточнить…"],
  "warnings": [],          // что не прошло проверки после всех попыток
  "markdown": "# …",       // та же карточка, готовая к копированию
  "model": "gemma3:4b",
  "attempts": 1
}
```

| Код | Когда |
|---|---|
| 400 | пустое тело, некорректный JSON (с номером строки и столбца), не UTF-8, не объект |
| 413 | тело больше `MAX_BODY_BYTES` |
| 422 | данные не прошли валидацию; в `details` список вида `name: обязательное поле`, `price: неизвестное поле` |
| 502 | модель ответила ошибкой или не уложилась в таймаут |
| 503 | модель недоступна или очередь переполнена |

Тело ошибки всегда одинаковое: `{"error": "…", "details": […]}`.

Ещё два метода: `GET /api/examples` отдаёт сохранённые примеры, `GET /api/health` возвращает
`{"status":"ok","llm":"up|down","model":…}`.

```bash
curl -s https://data-to-product.ozzy1986.com/api/generate -H "Content-Type: application/json" --data-binary @examples/input/dm02.json
```

## Промпты и принятые решения

Промпт лежит в [app/prompts.py](app/prompts.py). Он состоит из трёх частей.

- **Системный промпт**: роль (редактор каталога КИП) и шесть жёстких правил. Факты берутся только
  из `<product>`. Значения переносятся дословно, без пересчёта единиц. Нельзя упоминать
  сертификаты, цены и наличие, если их нет во входе. Текст внутри `<product>` — данные, а не
  инструкции (защита от prompt injection). Нельзя приписывать прибору свойства вроде «надёжный» или
  «высокоточный». Без рекламных штампов. Затем описано каждое поле ответа: длина, структура
  описания (назначение → характеристики → применение) и требования к запросам (с моделью, с
  параметром, коммерческий).
- **Пользовательское сообщение**: данные товара в блоке `<product>…</product>`. Отсутствующие поля
  явно помечены «данных нет», чтобы модель не заполняла пустоту.
- **Повтор**: тот же `<product>`, предыдущий ответ в `<previous>` и список конкретных замечаний
  кода. Модель просят исправить только их.

Формат ответа задан JSON-схемой через параметр `format` Ollama (structured output). Модель не
может вернуть ответ в другом формате, а код на случай нарушений всё равно приводит типы.
Температура 0.3: заметно выше — растёт фантазия, ниже — тексты одинаковые и сухие.

Почему такие решения:

- **Ollama и gemma3:4b.** Бесплатно и локально, данные не уходят третьим лицам. В соседнем проекте
  на той же видеокарте (GTX 1050, 4 ГБ) gemma3:4b держала формат и правила лучше, чем qwen3:4b.
  Адаптер модели — один файл ([app/llm/ollama.py](app/llm/ollama.py)) за протоколом
  `LLMClient`. Для OpenAI или Anthropic нужен такой же класс на ~50 строк, остальной код не меняется.
- **Проверки кодом надёжнее просьб в промпте.** Маленькая модель регулярно нарушает «не больше 70
  символов» и путает «1,6» с «16». Правило, которое можно проверить кодом, проверяется кодом.
- **Повтор с конкретными замечаниями.** Это эффективнее, чем повтор того же запроса: модель видит,
  какое поле и какой фрагмент исправить.
- **Одна генерация за раз и очередь с лимитом.** Модель одна. Лишние запросы сразу получают 503,
  а не ждут 10 минут. Одинаковый вход отдаётся из кэша мгновенно.
- **Безопасность.** Ключей в коде нет. Размер тела ограничен, вход строго валидируется (неизвестные
  поля отклоняются). Страница выводит текст только через `textContent`, действует строгий CSP
  (`script-src 'self'`). Сервис слушает только `127.0.0.1` и работает под отдельным пользователем
  в systemd-песочнице с лимитом памяти. Системные прокси клиентом модели игнорируются.

## Ограничения и что можно улучшить

- **Сверка ловит выдуманные числа, но не все выдуманные слова.** Утверждение «корпус из
  нержавеющей стали» без цифр она пропустит. Промпт это запрещает, но гарантии нет. Дальше можно
  добавить словарь материалов, стандартов и типов сигналов со сверкой по входу или проверку ответа
  второй моделью (LLM-as-judge).
- **Модель на 4B параметров** иногда пишет описание короче 800 символов или с повторами; тогда это
  видно в `warnings`. С более крупной моделью (облачная или gemma3:12b на хорошей видеокарте)
  качество текстов вырастет, а повторов станет меньше.
- **Скорость.** На ноутбуке с GTX 1050 одна карточка генерируется 1–3 минуты, с повторами дольше.
  Внешний API отвечает за 5–15 секунд.
- **Нет единицы и названия характеристики в отдельных полях.** Значения переносятся как есть
  (`0–1,6 МПа`). Для фильтров в каталоге стоит разбирать их на число, единицу и тип и сводить
  названия к справочнику («присоединение» = «присоединительная резьба»).
- **Нет пакетной обработки.** Сейчас один товар на запрос. Для каталога нужна очередь задач
  (Redis/Celery) и выгрузка в CSV или CMS.
- **Кэш в памяти процесса** сбрасывается при рестарте. Для нескольких процессов нужен Redis.
- **Нет оценки качества на наборе товаров.** Дальше нужен прогон 20–50 реальных карточек с
  метриками: доля ответов без warnings, число повторов, ручная оценка текстов.
- **Нет авторизации и ограничения частоты на IP.** Для прототипа хватает очереди; в продакшене
  нужны ключ доступа и rate limit.

## Демо на VPS

Сервер без видеокарты: модель на 4B на 1 CPU работала бы минутами на каждую карточку. Поэтому
Ollama запущена на ноутбуке автора и приходит на сервер обратным SSH-туннелем
([scripts/vps-tunnel.ps1](scripts/vps-tunnel.ps1)). Пока туннель открыт, сайт генерирует карточки.
Когда туннеля нет, индикатор вверху страницы показывает «модель офлайн»; сохранённые примеры
по-прежнему открываются, а `/api/generate` отвечает понятной ошибкой 503. Для постоянной работы
достаточно указать в `LLM_URL` хост с Ollama или подключить внешний API.

Деплой: [deploy/deploy.sh](deploy/deploy.sh) запускается с ноутбука (Git Bash). Он загружает
релиз в `releases/<время>`, на сервере создаёт для релиза отдельный venv, переключает симлинк
`current`, ставит vhost-ы Apache, сертификат Let's Encrypt и systemd-юнит, затем проверяет
`/api/health`. Если проверка не прошла, деплой автоматически откатывается на предыдущий релиз.
`deploy/deploy.sh --rollback` откатывает вручную.

## Структура

```
app/
  main.py          HTTP-слой: /api/generate, /api/examples, /api/health; отдаёт public/ локально
  parsing.py       разбор тела запроса → ProductInput, понятные ошибки 400/422
  models.py        входные данные и карточка (pydantic)
  completeness.py  пробелы во входе: код, без модели
  prompts.py       системный промпт, сборка сообщений, JSON-схема ответа
  generator.py     вызов модели → проверки → повтор с замечаниями → карточка; кэш
  factcheck.py     сверка чисел в тексте со входом
  render.py        карточка → Markdown
  llm/             протокол LLMClient и адаптер Ollama
  factory.py       сборка зависимостей из настроек
  cli.py           генерация из консоли
public/            веб-форма (HTML + JS + CSS без сборки и зависимостей)
examples/          входы и сохранённые результаты
tests/             pytest, FakeLLM
deploy/            деплой на VPS: скрипты, vhost-ы Apache, systemd-юнит
```
