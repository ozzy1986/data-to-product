# Карточка товара КИП из данных о приборе

Прототип сервиса: по JSON с данными о контрольно-измерительном приборе LLM пишет черновик
карточки товара для B2B-интернет-магазина:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1200 символов;
- таблица ключевых характеристик;
- 3–5 поисковых запросов;
- блок для менеджера: кому подходит прибор и какие задачи решает;
- список того, что нужно уточнить, и предупреждения о том, что не прошло автоматическую проверку.

Стек: Python 3.12+ и FastAPI, базы данных нет. Модель выбирается в файле `.env`, код менять не нужно:

- **Anthropic (Claude)** — через официальный SDK со structured outputs;
- **OpenAI или любой OpenAI-совместимый API** — OpenAI, Google Gemini, DeepSeek, OpenRouter, Groq,
  LM Studio, vLLM;
- **локальная модель через [Ollama](https://ollama.com)** — без ключа и без оплаты.

Разработка и подбор промпта шли на локальной `gemma3:4b` (видеокарта GTX 1050, 4 ГБ), примеры
результата в репозитории получены на ней. С облачной моделью тексты будут заметно лучше.

**Демо интерфейса:** https://data-to-product.ozzy1986.com — веб-форма и сохранённые примеры
(кнопки «Примеры»). Модель к демо-серверу не подключена, поэтому генерация там отвечает понятной
ошибкой 503; генерировать карточки нужно локально со своим ключом (ниже).

## Главное: модель не выдумывает характеристики

Одного промпта для этого мало, особенно с моделью на 4B параметров. Поэтому задача разделена между
моделью и кодом:

| Что | Кто делает | Почему так |
|---|---|---|
| Таблица характеристик | **код**, только из `specs` входа | значение в таблице физически не может прийти от модели |
| Характеристики, которых не хватает | модель называет **только названия**, код ставит значение «данных нет» | модель знает, что важно для манометра, но значений не пишет |
| Пробелы во входе (нет производителя, пустое значение, обрезанное описание) | **код**, ещё до вызова модели | детерминированно, не зависит от модели |
| Тексты: заголовок, описание, запросы, блок для менеджера | модель | для этого LLM и нужна |
| Сверка чисел в текстах со входом | **код** | каждое число в ответе должно встречаться во входных данных (`1,6` = `1.6`, `02` = `2`) |
| Оценки и свойства «от себя» | **код** | слова вроде «надёжный», «идеально», «устойчив», «агрессивн…», «сертифицирован» допустимы, только если их основа есть во входе |
| Десятичный разделитель | **код** | если во входе «1,6», то «1.6» в тексте модели исправляется на «1,6» без повторного вызова |
| Длина заголовка и описания, число запросов | **код** | маленькая модель плохо считает символы |

Если ответ не прошёл проверки, модель получает конкретные замечания и пишет ответ заново, максимум
`LLM_REPAIRS=2` раза. Замечания указывают поле и фрагмент: «search_queries: число «16» отсутствует во
входных данных (манометр 0 16 мпа)». Из всех попыток сервис берёт ответ с наименьшим числом проблем.
Что исправить не удалось, уходит в `warnings`: менеджер видит, какое место перепроверить.
Заголовок длиннее 70 символов код обрезает по границе слова и тоже пишет об этом в `warnings`.

## Быстрый старт: проверка со своим ключом

Нужен Python 3.12+. На Linux и macOS вместо `.venv/Scripts/` пишется `.venv/bin/`.

```bash
git clone https://github.com/ozzy1986/data-to-product.git
```

```bash
cd data-to-product
```

```bash
python -m venv .venv
```

```bash
.venv/Scripts/pip install -r requirements-dev.txt
```

```bash
cp .env.example .env
```

В `.env` оставьте нужного провайдера и впишите ключ в `LLM_API_KEY`. По умолчанию в шаблоне
выбран Anthropic. Если ключ уже лежит в `ANTHROPIC_API_KEY` или `OPENAI_API_KEY`, `LLM_API_KEY`
можно не заполнять: сервис возьмёт привычную переменную провайдера.

Сгенерировать карточку прямо в консоли:

```bash
.venv/Scripts/python -m app.cli examples/input/dm02.json
```

Или открыть веб-форму на http://127.0.0.1:8103:

```bash
.venv/Scripts/python -m uvicorn app.main:app --port 8103
```

Индикатор вверху страницы показывает, доступна ли модель. Если ключ неверный, модель не найдена
или нет сети, форма и API отвечают понятной ошибкой: «API Anthropic отклонил ключ: проверьте
LLM_API_KEY», «модель … не найдена: проверьте LLM_MODEL».

### Провайдеры

| `LLM_PROVIDER` | `LLM_URL` | `LLM_MODEL` по умолчанию | Ключ |
|---|---|---|---|
| `anthropic` | не нужен | `claude-opus-5-5` | `LLM_API_KEY` или `ANTHROPIC_API_KEY` |
| `openai` | `https://api.openai.com/v1` | `gpt-4o-mini` | `LLM_API_KEY` или `OPENAI_API_KEY` |
| `ollama` | `http://127.0.0.1:11434` | `gemma3:4b` | не нужен |

Через `openai` работают и другие совместимые API. Нужно задать `LLM_URL` и `LLM_MODEL`:

| Сервис | `LLM_URL` | `LLM_MODEL` (например) |
|---|---|---|
| Google Gemini | `https://generativelanguage.googleapis.com/v1beta/openai` | `gemini-2.0-flash` |
| DeepSeek | `https://api.deepseek.com` | `deepseek-chat` |
| OpenRouter | `https://openrouter.ai/api/v1` | любая из каталога |
| Ollama в режиме OpenAI | `http://127.0.0.1:11434/v1` | `gemma3:4b` |

Названия моделей у провайдеров меняются. Если модель по умолчанию снята с поддержки, сервис
ответит «модель … не найдена», и достаточно указать актуальную в `LLM_MODEL`.

Ключ берётся только из окружения или `.env`, в коде и в репозитории его нет (`.env` в
`.gitignore`). В логи и `repr` настроек ключ не попадает. Переменные, заданные в системе, важнее
`.env`.

**Что проверено.** С Ollama сервис работал вживую: на ней подбирался промпт. Клиенты Anthropic и
OpenAI проверены тестами против поддельного HTTP-сервера: формат запроса, заголовок с ключом,
разбор ответа, ошибки (неверный ключ, нет модели, лимит запросов, перегрузка, отказ модели, битый
JSON). С платными ключами они не запускались, потому что их у автора нет.

### Из консоли

`python -m app.cli файлы…` печатает Markdown. С флагом `--json` выводится JSON, с `--out
examples/output` для каждого входного файла сохраняются `<имя>.json` и `<имя>.md`. Именно так
получены примеры в репозитории.

### Тесты

```bash
.venv/Scripts/python -m pytest -q
```

77 тестов работают без модели, без ключей и без сети. В генератор вместо модели подставляется
`FakeLLM` с заранее заданными ответами. Клиенты всех трёх провайдеров проверяются против
поддельного HTTP-сервера (`MockTransport`). Проверяются:

- разбор и валидация входа, поиск пробелов;
- сверка чисел и оценочных слов, повтор с замечаниями, выбор лучшей попытки, обрезка заголовка;
- кэш и коды ответов API;
- формат запросов к API провайдеров и толкование их ошибок: неверный ключ, лимит, сбой, битый JSON, таймаут;
- чтение `.env` и выбор провайдера.

### Настройки (переменные окружения)

| Переменная | По умолчанию | Что это |
|---|---|---|
| `LLM_PROVIDER` | `ollama` | `anthropic`, `openai` или `ollama` |
| `LLM_API_KEY` | пусто | ключ API (или `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`) |
| `LLM_MODEL` | по провайдеру | модель |
| `LLM_URL` | по провайдеру | базовый адрес API |
| `LLM_TIMEOUT` | `240` | секунд на один вызов модели |
| `LLM_NUM_CTX` | `4096` | только Ollama: контекст; промпту с повтором хватает, и модель целиком помещается в 4 ГБ видеопамяти |
| `LLM_REPAIRS` | `2` | сколько раз повторять запрос с замечаниями |
| `LLM_TEMPERATURE` | `0.3` | температура (Ollama и OpenAI; текущие модели Claude её не принимают) |
| `LLM_CONCURRENCY` | `1` | сколько карточек генерируется одновременно; для облачной модели можно 4 и больше |
| `QUEUE_LIMIT` | `4` | сколько запросов ждут модель; при переполнении сразу 503, без долгого таймаута |
| `CACHE_SIZE` | `256` | готовых карточек в памяти (ключ — хэш входа, модели и версии промпта) |
| `MAX_BODY_BYTES` | `64000` | предельный размер запроса |

## API

`POST /api/generate` с телом в виде JSON о товаре:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {"диапазон измерений": "0–1,6 МПа", "класс точности": "1,5", "присоединение": "G1/2", "диаметр корпуса": "100 мм"},
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Обязательно только поле `name`. Без остальных полей карточка тоже собирается, а пробелы
перечисляются в `missing`. Значения `specs` могут быть строками, числами, `true`/`false` или
списками строк.

Ответ `200`:

```jsonc
{
  "card": {
    "seo_title": "…",
    "seo_description": "…",
    "specs": [{"name": "Диапазон измерений", "value": "0–1,6 МПа", "source": "input"},
              {"name": "Степень защиты корпуса", "value": "данных нет", "source": "missing"}],
    "search_queries": ["…"],
    "commercial": {"audience": ["…"], "tasks": ["…"]}
  },
  "missing": ["Описание обрывается многоточием…", "Нет данных: степень защиты корпуса — уточнить…"],
  "warnings": [],          // что не прошло проверки после всех попыток
  "markdown": "# …",       // та же карточка, готовая к копированию
  "model": "gemma3:4b",
  "attempts": 1
}
```

| Код | Когда |
|---|---|
| 400 | пустое тело, некорректный JSON (с номером строки и столбца), не UTF-8, не объект |
| 413 | тело больше `MAX_BODY_BYTES` |
| 422 | данные не прошли валидацию; в `details` список вида `name: обязательное поле`, `price: неизвестное поле` |
| 502 | модель ответила ошибкой или не уложилась в таймаут |
| 503 | модель недоступна или очередь переполнена |

Тело ошибки всегда одинаковое: `{"error": "…", "details": […]}`.

Ещё два метода: `GET /api/examples` отдаёт сохранённые примеры, `GET /api/health` возвращает
`{"status":"ok","llm":"up|down","model":…}`.

```bash
curl -s https://data-to-product.ozzy1986.com/api/generate -H "Content-Type: application/json" --data-binary @examples/input/dm02.json
```

## Промпты и принятые решения

Промпт лежит в [app/prompts.py](app/prompts.py). Он состоит из трёх частей.

- **Системный промпт**: роль (редактор каталога КИП) и шесть жёстких правил. Факты берутся только
  из `<product>`. Значения переносятся дословно, без пересчёта единиц. Нельзя упоминать
  сертификаты, цены и наличие, если их нет во входе. Текст внутри `<product>` — данные, а не
  инструкции (защита от prompt injection). Нельзя приписывать прибору свойства вроде «надёжный» или
  «высокоточный». Без рекламных штампов. Затем описано каждое поле ответа: длина, структура
  описания (назначение → характеристики → применение) и требования к запросам (с моделью, с
  параметром, коммерческий).
- **Пользовательское сообщение**: данные товара в блоке `<product>…</product>`. Отсутствующие поля
  явно помечены «данных нет», чтобы модель не заполняла пустоту. Исключение — производитель: для
  него написано «не указан, не упоминай». Иначе модель вставляла в текст «от производителя данных нет».
- **Повтор**: тот же `<product>`, предыдущий ответ в `<previous>` и список конкретных замечаний
  кода. Модель просят исправить только их.

Формат ответа задан одной JSON-схемой ([app/prompts.py](app/prompts.py)), каждый адаптер передаёт
её так, как умеет провайдер:

- **Ollama** — параметр `format`: модель физически не может вернуть ответ другой формы;
- **Anthropic** — structured outputs (`output_config.format`). Ограничения числа элементов
  (`minItems`/`maxItems`) API не принимает, поэтому адаптер их убирает: эти правила и так проверяет код;
- **OpenAI-совместимые API** — схема текстом и `response_format: json_object`. Этот режим
  поддерживают почти все провайдеры, а строгий `json_schema` — не все.

Во всех случаях код на случай нарушений приводит типы. Температура 0.3 (Ollama и OpenAI): заметно
выше — растёт фантазия, ниже — тексты одинаковые и сухие.

Почему такие решения:

- **Ollama и gemma3:4b.** Бесплатно и локально, данные не уходят третьим лицам. В соседнем проекте
  на той же видеокарте (GTX 1050, 4 ГБ) gemma3:4b держала формат и правила лучше, чем qwen3:4b.
- **Модель подключается через порт.** Генератор знает только протокол `LLMClient`
  (`generate_json`, `is_up`). Адаптеров три: [ollama.py](app/llm/ollama.py),
  [openai.py](app/llm/openai.py) и [claude.py](app/llm/claude.py). Каждый переводит ошибки
  провайдера в две понятные сервису: «модель недоступна» (503) и «ошибка модели» (502). Новый
  провайдер — ещё один такой класс, генератор и API не меняются. SDK провайдера импортируется,
  только когда он выбран.
- **OpenAI-совместимый протокол** покрывает большинство провайдеров одним адаптером на чистом HTTP.
  Для Claude используется официальный SDK: он сам повторяет запросы при 429 и 5xx с учётом
  `retry-after` и поддерживает structured outputs.
- **Проверки кодом надёжнее просьб в промпте.** Маленькая модель регулярно нарушает «не больше 70
  символов» и путает «1,6» с «16». Правило, которое можно проверить кодом, проверяется кодом.
- **Повтор с конкретными замечаниями.** Это эффективнее, чем повтор того же запроса: модель видит,
  какое поле и какой фрагмент исправить.
- **Одна генерация за раз и очередь с лимитом.** Модель одна. Лишние запросы сразу получают 503,
  а не ждут 10 минут. Одинаковый вход отдаётся из кэша мгновенно.
- **Безопасность.** Ключей в коде нет. Размер тела ограничен, вход строго валидируется (неизвестные
  поля отклоняются). Страница выводит текст только через `textContent`, действует строгий CSP
  (`script-src 'self'`). Сервис слушает только `127.0.0.1` и работает под отдельным пользователем
  в systemd-песочнице с лимитом памяти. Клиент локальной Ollama игнорирует системные прокси.

### Что пробовали и от чего отказались

Варианты промпта сравнивались на трёх примерах с gemma3:4b:

- **Эталонная карточка в промпте (few-shot).** Заголовки стали длиннее, стиль суше, но модель
  начала переносить факты из эталона. В задачах манометра появился «учёт расхода теплоносителей»
  из примера с расходомером. Промпт вырос вдвое, и генерация заметно замедлилась. Убрали.
- **Описание массивом из трёх абзацев в схеме.** Абзацы получались всегда, но описания стали
  короче: модель пишет короткие абзацы, и чаще требовался повтор из-за длины. Ограничение длины
  абзаца в схеме (`minLength`/`maxLength`) держит объём, но Ollama обрывает текст на полуслове.
  Вернули одну строку.
- **Запрещённые слова примерами в правилах** («не пиши „идеально подходит“») иногда работают как
  подсказка: модель пишет ровно их. Поэтому оценочные слова ловит код, а не промпт.

## Ограничения и что можно улучшить

- **Сверка ловит выдуманные числа и частые оценочные слова, но не все выдуманные утверждения.**
  Фразу «корпус из нержавеющей стали» без цифр и без слов из стоп-списка она пропустит. Промпт это
  запрещает, но гарантии нет. Дальше можно добавить словарь материалов, стандартов и типов сигналов
  со сверкой по входу или проверку ответа второй моделью (LLM-as-judge).
- **Число сверяется со входом, но не с местом, где оно стоит.** Запрос «датчик 100 кпа» пройдёт
  проверку, если 100 встречается во входе в другом значении (`+100 °C`). Строже было бы сверять
  пары «число + единица».
- **Сопоставление названий характеристик грубое** (по первым 5 буквам слов, без морфологии).
  Модель может назвать недостающей характеристику, которая во входе записана другими словами.
  Лучше вести справочник характеристик по типам приборов.
- **Модель на 4B параметров** иногда пишет описание короче 800 символов или с повторами; тогда это
  видно в `warnings`. С более крупной моделью (облачная или gemma3:12b на хорошей видеокарте)
  качество текстов вырастет, а повторов станет меньше.
- **Скорость.** На ноутбуке с GTX 1050 одна карточка генерируется 1–3 минуты, с повторами дольше.
  Облачный API отвечает обычно за секунды или десятки секунд.
- **Промпт подбирался на одной модели.** Правила и проверки отлаживались на gemma3:4b. С другой
  моделью стоит прогнать примеры и посмотреть на `warnings`: сильная модель, скорее всего,
  пройдёт проверки с первой попытки.
- **Дообучение (fine-tuning).** Когда у магазина накопятся сотни вычитанных редакторами карточек,
  на них можно дообучить небольшую модель (LoRA). Она будет писать в стиле каталога, и промпт
  станет короче. Для прототипа таких данных нет.
- **Нет единицы и названия характеристики в отдельных полях.** Значения переносятся как есть
  (`0–1,6 МПа`). Для фильтров в каталоге стоит разбирать их на число, единицу и тип и сводить
  названия к справочнику («присоединение» = «присоединительная резьба»).
- **Нет пакетной обработки.** Сейчас один товар на запрос. Для каталога нужна очередь задач
  (Redis/Celery) и выгрузка в CSV или CMS.
- **Кэш в памяти процесса** сбрасывается при рестарте. Для нескольких процессов нужен Redis.
- **Нет оценки качества на наборе товаров.** Дальше нужен прогон 20–50 реальных карточек с
  метриками: доля ответов без warnings, число повторов, ручная оценка текстов.
- **Нет авторизации и ограничения частоты на IP.** Для прототипа хватает очереди; в продакшене
  нужны ключ доступа и rate limit.

## Демо на VPS

https://data-to-product.ozzy1986.com показывает интерфейс и сохранённые примеры. Модель к серверу
не подключена: на сервере нет видеокарты, а платного ключа у автора нет. Поэтому индикатор вверху
страницы показывает «модель офлайн», а `/api/generate` отвечает понятной ошибкой 503. Чтобы сайт
генерировал карточки, достаточно прописать провайдера и ключ в `shared/.env` на сервере.

Во время разработки к серверу подключалась Ollama с ноутбука автора через обратный SSH-туннель
([scripts/vps-tunnel.ps1](scripts/vps-tunnel.ps1)).

Деплой: [deploy/deploy.sh](deploy/deploy.sh) запускается с ноутбука (Git Bash). Он загружает
релиз в `releases/<время>`, на сервере создаёт для релиза отдельный venv, переключает симлинк
`current`, ставит vhost-ы Apache, сертификат Let's Encrypt и systemd-юнит, затем проверяет
`/api/health`. Если проверка не прошла, деплой автоматически откатывается на предыдущий релиз.
`deploy/deploy.sh --rollback` откатывает вручную.

## Структура

```
app/
  main.py          HTTP-слой: /api/generate, /api/examples, /api/health; отдаёт public/ локально
  parsing.py       разбор тела запроса → ProductInput, понятные ошибки 400/422
  models.py        входные данные и карточка (pydantic)
  completeness.py  пробелы во входе: код, без модели
  prompts.py       системный промпт, сборка сообщений, JSON-схема ответа
  generator.py     вызов модели → проверки → повтор с замечаниями → карточка; кэш
  factcheck.py     сверка чисел в тексте со входом
  render.py        карточка → Markdown
  llm/             протокол LLMClient; адаптеры Ollama, OpenAI-совместимого API и Anthropic
  factory.py       сборка зависимостей из настроек
  cli.py           генерация из консоли
public/            веб-форма (HTML + JS + CSS без сборки и зависимостей)
examples/          входы и сохранённые результаты
tests/             pytest, FakeLLM
deploy/            деплой на VPS: скрипты, vhost-ы Apache, systemd-юнит
```
